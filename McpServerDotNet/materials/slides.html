MCP architecture

The model never talks to the server directly. The host decides what to call, what to approve, what to show.

Three roles: host (VS Code), one MCP client per server (1:1), MCP server. Messages are JSON-RPC. Key angle: the model only proposes; the host runs the call, asks for approval, decides what goes into context.

Transports: local vs remote

stdio (local)

  • Host starts the server as a local process
  • Runs in the user's environment, single user
  • Auth is outside the spec (env vars, local credentials)

Streamable HTTP (remote)

  • Server runs somewhere else, many users and clients
  • MCP authorization applies (OAuth 2.1)
  • Today's demo: http://localhost:5080/mcp
stdio: local process, the user's own environment, auth not covered by the spec. Streamable HTTP: remote, multi-user, and this is where the MCP authorization spec applies. The demo uses HTTP.

Deployment variants

Three ways to add MCP to an existing API. (a) in-process next to the API, sharing the domain: this is the demo. (b) sidecar calling REST: API untouched, but an extra hop. (c) local stdio wrapper over REST: quick, but per machine and auth is on you. Only (a) is in the demo; (b) and (c) are slide-only.

What MCP adds to OAuth

Red = what MCP adds: PRM discovery, audience binding, mandatory PKCE

The team knows OAuth; skip the basics. Roles: Keycloak = Authorization Server (open-source IAM server, runs as a container in Aspire), MCP server = Protected Resource, VS Code / Inspector = client. Point at the red steps: the client discovers the AS from the 401 via PRM (no config), the token is bound to this MCP server via resource / aud, PKCE is mandatory. Keycloak is one of many authorization servers. With Entra ID the protocol is the same; configuration, claim format (audience, roles) and client registration differ.

API key vs OAuth

API key

  • Shared secret
  • No per-user identity, no roles
  • Simple
  • Fits: service-to-service, internal

OAuth (MCP authorization)

  • Per-user identity
  • Roles (e.g. dispatcher)
  • Discovery lets the client drive the login
  • Fits: many users, remote, shared server
A static bearer header is not MCP authorization.

Live: scene 6 (+ optional scene 7)

We use both in the team; this is about when each fits an MCP server, not which is better. API key: shared secret in a header, legal, but no discovery, no audience binding, no per-user identity. Now that you have seen it: the shortcuts we took on purpose. http on localhost; only /mcp is protected, REST is another adapter; clients are pre-registered in Keycloak, a public server would need DCR or CIMD; data lives in memory.

Why MCP?

  • Discovery: schemas and descriptions, no hand-written instructions
  • Curated surface + per-tool approval
  • Standard auth: PRM discovery, per-user identity, roles
  • Task-shaped interface: fewer calls, less context, readable domain errors
  • Portability across clients (VS Code, Inspector, others)

Concession: 1:1 wrappers add little (get_drivers).

vs skills + scripts: different layers; MCP when you need identity, shared or remote access

A1. MCP vs skills + scripts

  • Token cost: conceded. Skills load only name/description upfront; MCP clients load all tool definitions every turn. Small with 5 tools, grows with many servers.
  • Different layers. A skill is knowledge and procedure; MCP is access to a system. The script still calls the API.
  • Where skill + script loses: identity and roles (key in env, no per-user login); distribution (runs on every machine vs deployed once); surface and approval (a shell command vs dispatch_order).
  • Honest: portability is weaker now; Agent Skills are an open standard.
  • Rule of thumb: local, single-user, token budget matters → skill + script. Shared, remote, many users, identity and roles → MCP. Often both.
Only if asked. Concede tokens first: skills use progressive disclosure; Anthropic itself proposes "code execution with MCP" (150k to 2k tokens in their example, at the cost of a sandbox). Then: different layers; the script is the "agent calls REST" path again. Losses: identity (bob vs alice), distribution, approval of a domain operation. Close: often both, the skill teaches the procedure and MCP provides access.
